# Deployment: Vercel (frontend) + Render (backend)

The frontend is a static/SSR Next.js app and fits Vercel. The backend does **not**: it parses PDFs with
PyMuPDF, runs extraction jobs that take minutes, runs a polling worker loop, and writes uploaded PDFs and
cropped figures to disk. Vercel functions are ephemeral and time-limited, so the API runs as a container
on Render with a persistent disk, and Vercel only serves the UI.

```
Vercel          frontend/          Next.js 16, NEXT_PUBLIC_API_URL -> Render
Render (web)    backend/           FastAPI + embedded extraction worker + 5GB disk at /data
Neon            Postgres           external, free tier
```

## Swapping the database

Nothing in the app is tied to a specific database. The two Postgres-specific constructs both degrade
on their own: `JSONB` is declared as `JSON().with_variant(JSONB(), "postgresql")`, and the worker's
`SELECT … FOR UPDATE SKIP LOCKED` claim renders without the locking clause on dialects that lack it.
So changing database is a one-line `DATABASE_URL` change, with these caveats:

| Option | Notes |
| --- | --- |
| **Neon** (used here) | Real Postgres, free tier that does not expire. Scales to zero; the first request after idle pays a short wake-up, which `pool_pre_ping=True` in `app/db.py` already absorbs. |
| Supabase | Also real Postgres. Free projects pause after inactivity and need a manual resume. |
| Render Postgres | The `free` plan expires and is then deleted. Fine for a demo, not for real data. |
| SQLite on the disk | `DATABASE_URL=sqlite:////data/exam.db` (four slashes = absolute path). No database service at all. **Single instance only**, and `SKIP LOCKED` is dropped, so never run more than one worker. Writes during extraction can make readers hit `database is locked`. |
| MySQL / MariaDB | Works, but add a driver (e.g. `pymysql`) to `requirements.txt` first — none is installed. |
| MongoDB / other non-SQL | Not viable without a rewrite; the whole data layer is SQLAlchemy relational. |

## 0. Push to GitHub

Both hosts deploy from a Git repository. This project is not a repo yet:

```bash
git init
git add .
git commit -m "ExamForge: initial commit"
git branch -M main
git remote add origin git@github.com:<you>/<repo>.git
git push -u origin main
```

`.gitignore` already excludes `.env`, `backend/exam.db`, `backend/storage/` and `node_modules/`.
Confirm with `git status` that no `.env` file and no `exam.db` are staged before you push.

## 1. Backend on Render

First create the database on Neon (https://neon.tech): new project → copy the connection string.
Take the **direct** string, not the `-pooler` one — this is a long-lived process with its own
SQLAlchemy pool, not a serverless function. It looks like:

```
postgresql://user:password@ep-xxx-xxx.region.aws.neon.tech/dbname?sslmode=require
```

`app/config.py` rewrites that to the psycopg 3 driver automatically, and keeps `?sslmode=require`.
The `postgres://` form works too. Tables are created on first boot, so there is nothing to import.

Then Render reads [`render.yaml`](../render.yaml) at the repo root, which declares the API service and
its disk.

1. Render dashboard → **New → Blueprint** → pick the repo → **Apply**.
2. Render prompts for the values marked `sync: false`. Set:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | the Neon connection string above |
   | `GEMINI_API_KEY` | your key from https://aistudio.google.com/apikey |
   | `ADMIN_EMAIL` | your real admin email |
   | `ADMIN_PASSWORD` | a strong password (this seeds the bootstrap admin on first boot) |
   | `CORS_ORIGINS` | leave blank for now; set in step 3 |

   `JWT_SECRET` is generated by Render.
3. Wait for the first deploy, then check `https://<your-api>.onrender.com/api/health` returns `{"ok":true}`.
   Copy that base URL.

No Gemini key yet? Set `EXTRACTION_PROVIDER=heuristic` to use the offline regex extractor — it only
handles clean, conventional layouts, but the rest of the app works.

### Picking Gemini models

`render.yaml` ships `gemini-3.5-flash` for both extraction and verification, with a fallback chain.
Three things decide this, and they change often — check with the key you actually deploy:

- **`gemini-2.5-*` is retired for new API keys.** It still appears in `models.list()` but returns
  `404 ... no longer available to new users` on `generateContent`.
- **Free-tier keys have no Pro quota.** `gemini-3.1-pro-preview` and `gemini-pro-latest` return
  `429 RESOURCE_EXHAUSTED`, so the verification pass must use Flash until you are on a paid key. On a
  paid key, set `GEMINI_VERIFY_MODEL` to a Pro model — it is the accuracy safeguard for flagged questions.
- **Flash models return `503` under load.** This is routine, not a failure. `GEMINI_FALLBACK_MODELS` is
  tried in order on 429/503, which is why the chain is set rather than left empty.

List what a key can actually reach:

```bash
cd backend && .venv/bin/python -c "
from app.config import get_settings
from google import genai
for m in genai.Client(api_key=get_settings().gemini_api_key).models.list():
    if 'generateContent' in (getattr(m,'supported_actions',None) or []): print(m.name)
"
```

### Plan notes

- The API service is on `starter` because **a Render disk requires a paid instance type**. On `free`
  there is no persistent storage, so uploaded PDFs and cropped figures vanish on every restart. This is
  the one unavoidable cost; removing it means porting `app/storage.py` to S3-compatible object storage.
- The database is on Neon's free tier, so it is not the thing that expires. Check Neon's current storage
  and compute limits against your usage — these tiers change.
- Back up the Neon database (Neon has its own backup/branching) **and** the Render disk. The uploaded
  PDFs on that disk are the only copy of your source papers.

## 2. Frontend on Vercel

1. Vercel → **Add New → Project** → import the same repo.
2. **Root Directory: `frontend`** — this is the one setting that matters; Vercel defaults to the repo
   root and the build fails there. Framework preset auto-detects as Next.js.
3. Environment variable: `NEXT_PUBLIC_API_URL` = the Render URL from step 1, no trailing slash
   (e.g. `https://examforge-api.onrender.com`).
4. Deploy, then copy the resulting `https://<project>.vercel.app` URL.

`NEXT_PUBLIC_*` values are baked in at build time, so **changing it later needs a redeploy**, not just a
settings save.

## 3. Close the loop on CORS

Back in Render → the API service → Environment → set:

```
CORS_ORIGINS=https://<project>.vercel.app
```

Comma-separate if you add a custom domain: `https://app.example.com,https://<project>.vercel.app`.
JSON (`["https://…"]`) is accepted too. Save — Render redeploys. Without this the browser blocks every
API call from the deployed frontend.

Then open the Vercel URL, sign in with `ADMIN_EMAIL` / `ADMIN_PASSWORD`, and upload a paper.

## What to know before real traffic

- **Schema changes.** Tables are created with `create_all` on startup, and `add_missing_columns()` adds
  new nullable columns. Anything else (type changes, constraints, drops) needs Alembic. Add it before
  the first breaking schema change.
- **One API host only.** Storage is local disk ([`app/storage.py`](../backend/app/storage.py)), so the
  disk pins you to a single instance — do not scale the web service past 1. To scale out, port
  `storage.py` to S3/GCS, then you can drop the disk, split the worker into its own Render service
  (`python -m app.worker`, `EMBEDDED_WORKER=false`) and raise the instance count. The workers claim jobs
  with `SELECT … FOR UPDATE SKIP LOCKED`, so many of them against one Postgres is already safe.
- **Extraction competes with requests.** `EMBEDDED_WORKER=true` runs extraction in the API process.
  On a small instance a large PDF will slow API responses. Lower `EXTRACTION_CONCURRENCY` if it hurts.
- **Cost of Gemini.** `GEMINI_VERIFY_MODEL` (Pro) re-reads flagged questions. `MAX_VERIFY_CALLS` caps it
  per document; lower it to cut spend.
